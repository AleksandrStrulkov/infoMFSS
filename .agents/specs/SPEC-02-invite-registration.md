# SPEC-02: Регистрация по одноразовым приглашениям

## 1. Цель
Закрыть свободную регистрацию и отказаться от email-активации: действующий сотрудник выпускает одноразовую ссылку на 48 часов, приглашённый регистрируется и сразу входит в приложение. Сохранить восстановление пароля через email и публичный канал запроса доступа через существующую форму обратной связи.

## 2. Границы задачи (Scope)
- Входит:
  - Защитить корень `/` авторизацией; для анонимного гостя — перенаправление на `users:login` с `next=/`, для вошедшего — прежняя главная страница.
  - На входе оставить форму и ссылку сброса пароля, убрать публичную регистрацию, показать сообщение о закрытом доступе и ссылку «Запросить доступ» на `mfss:contact` (`/contact/`). Проверить, что публичная форма контакта действительно доступна анонимным пользователям.
  - Модель инвайта, миграция, сервисы выпуска и погашения, ограничение числа действующих инвайтов на автора, просмотр своих активных ссылок и приглашённых коллег в профиле.
  - Регистрация только по действительному токену; активный аккаунт без письма активации, автоматический вход, редирект на `mfss:home`.
  - Удалить возможность email-активации через старый публичный маршрут; убрать старые публичные ссылки на регистрацию, включая шаблон ошибки активации. Обновить тесты прежней активации на новую политику.
- НЕ входит:
  - Изменение схем шахт, оборудования, кабельных трасс, React/Vite и их JSON; SMS-авторизация, импорт пользователей, рассылка приглашений по почте, массовая выдача и управление чужими инвайтами.
  - Переделка восстановления/смены пароля и удаления существующих `AllowedPerson`/`is_activated` из БД: старые данные и иные потребители не должны ломаться. Административное создание пользователей сохраняет штатный механизм Django.
- Принятый предел: `N = 5` одновременно действующих (неиспользованных и неистекших) приглашений на автора; значение оформить именованной константой сервиса, без новой переменной окружения.

## 3. Входные и выходные данные (Контракт)
- Серверные HTML-страницы, не JSON API; стандартный Django test client, CSRF для POST. Токен передаётся только как сегмент пути; данные регистрационной формы — `application/x-www-form-urlencoded`.
- `GET /` (`mfss:home`): вошедшему `200` с прежним контентом; гостю `302` на `/users/?next=/`. Уточнение: фактический `users:login` сейчас расположен на `/users/`, не на `/login/`; для требования о `/login/` добавить канонический публичный alias `/login/` для того же LoginView, сохранив существующий `users:login` как совместимый маршрут либо перенести имя `users:login` на новый адрес и оставить старый redirect. Выбранный контракт: `users:login` → `/login/`, старый `GET /users/` → `302 /login/` с сохранением безопасного `next` и поддержкой прежних POST-клиентов через LoginView/redirect 307 только при явной необходимости. Проверить отсутствие конфликтов маршрутов в `config/urls.py`. `LOGIN_URL` оставить именованным.
- `GET /login/` (`users:login`): `200`, форма, ссылка `users:password_reset`, нет ссылки на регистрацию, ссылка `mfss:contact`; `POST /login/` сохраняет существующую авторизацию. Не делать открытых редиректов через `next`.
- `POST /users/accounts/invites/` (`users:invite_create`): только авторизованному пользователю, CSRF; без payload, создает один инвайт, `302` на `users:profile` (PRG); при достижении N — понятное сообщение без создания записи и тот же редирект; гостю — `302` на вход. `GET` по этому адресу не выпускает инвайт (`405`).
- `GET /users/accounts/profile/` (`users:profile`): только автору, `200` с кнопкой выпуска, активными ссылками (абсолютный URL, «Копировать», время окончания) и историей использованных инвайтов (ФИО, при отсутствии имени — email как идентификатор, дата регистрации `date_joined`). Чужие инвайты не показывать; просроченные не входят в активный список; токены погашенных ссылок не показывать в истории.
- `GET|POST /users/accounts/register/` без токена (`users:register_without_token`): `200` с объяснением и ссылкой `mfss:contact`, **без формы**; POST ничего не создает (допустим `405` либо `200` с тем же сообщением, но без формы). Не позволять старому `RegisterView` принимать публичный POST.
- `GET|POST /users/accounts/register/<str:token>/` (`users:register`): токен — криптографически случайная URL-safe строка; строгая проверка формата/длины до обращения к БД. Отсутствующий, неверный, использованный или истёкший токен возвращает `200` с отдельной страницей ошибки и «Запросить доступ», без формы и без раскрытия состояния/существования токена; для произвольного битого URL, не соответствующего маршруту, допустим `404`, но публичная регистрация не открывается. Валидный GET возвращает `200` с текущими полями регистрации (`last_name`, `first_name`, `middle_name`, `email`, `phone`, `location_of_work`, `post`, `password1`, `password2`) и ФИО пригласившего. POST с ошибками полей — `200` с формой и ошибками без погашения инвайта; успешный POST — `302` на `mfss:home`, пользователь аутентифицирован.
- После регистрации `is_active=True` и `is_activated=True` (согласовать существующие флаги), `used_at` и `registered_user` записаны в той же транзакции. Повторный POST с тем же токеном не создаёт пользователя, не логинит второго клиента и показывает ту же безопасную ошибку.
- Старый `/users/accounts/activate/<path:sign>` не должен менять состояние пользователя: удалить маршрут либо оставить ответ с сообщением о закрытой активации, без вызова `user_activate`. Ссылки восстановления пароля (`users:password_reset*`) и email-сообщения сброса продолжают работать.

## 4. Требования к данным и БД
- Затронутые модели: `users.User` как действующий `AUTH_USER_MODEL`; новая `users.Invitation` (имя условное, согласовать в реализации). Миграция: **Да**, только новая таблица/индексы и ограничения; существующие предметные модели не мигрировать.
- Поля: `token` — уникальная URL-safe строка с энтропией не менее 256 бит (например, `secrets.token_urlsafe(32)`, `CharField(max_length=64, unique=True)`); `created_by` — FK на `settings.AUTH_USER_MODEL`, `related_name='created_invitations'`, `on_delete=PROTECT`; `created_at` — `DateTimeField(default=timezone.now)`; `expires_at` — `DateTimeField`, устанавливать при выпуске `created_at + timedelta(hours=48)`; `used_at` — nullable timestamp; `registered_user` — nullable `OneToOneField(settings.AUTH_USER_MODEL, on_delete=PROTECT, related_name='registration_invitation')` (уникальность не даёт одному аккаунту связаться с двумя инвайтами). Для связности `used_at` и `registered_user` задать `CheckConstraint`: оба NULL или оба NOT NULL. Удаление автора/зарегистрированного пользователя блокируется PROTECT ради истории; продуктовый сценарий удаления пользователей при необходимости проработать отдельно.
- Проверка действительности: `used_at IS NULL`, `registered_user IS NULL`, `expires_at > timezone.now()` (ровно в момент окончания уже просрочен); отдельный status-field не нужен, состояние выводится из этих полей и времени. Индекс по токену обеспечивает unique constraint; дополнительный составной индекс `(created_by, used_at, expires_at)` для профиля/квоты и индекс для выборки истории по автору (проверить реальный план запросов до добавления избыточного). Не индексировать динамическое понятие «активный» отдельным флагом.
- Выборки профиля и регистрации: `select_related('created_by')` при показе пригласившего и `select_related('registered_user')` при истории; фильтр только `created_by=request.user`, сортировка по `created_at`/`used_at`, без N+1.
- Выпуск ссылки: `transaction.atomic()`, `select_for_update()` **строки автора** перед подсчётом действующих инвайтов; под PostgreSQL это сериализует параллельный выпуск одним автором даже при отсутствии инвайтов. Подсчёт только неиспользованных с `expires_at > now`, `N=5`; создать запись в той же транзакции. Для выпуска использовать `secrets`, не `random`, уникальность токена закрепить БД. Формировать абсолютный URL из `reverse('users:register', kwargs={'token': ...})` с корректной схемой/хостом через настроенные trusted host/proxy settings; не подставлять непроверенный Host и не логировать токен.
- Погашение: `transaction.atomic()` вокруг блокировки `Invitation.objects.select_for_update()` по токену, повторной проверки срока/статуса на момент POST, сохранения пользователя и `used_at`/`registered_user`. Валидация формы может выполняться до захвата блокировки, но решение о погашении — только внутри блокировки; уникальные ограничения email/инвайта и IntegrityError обрабатывать без утечки деталей и без частично созданного пользователя. Вход выполнять после успешного commit; не посылать писем активации внутри или вне транзакции. Гонку проверять на PostgreSQL: SQLite не обеспечивает эквивалентную блокировку `select_for_update`.

## 5. Требования к качеству (Acceptance Criteria)
- [ ] Покрыто unit-тестами (слой services/domain): выпуск, валидность до/ровно/после 48 часов, N=5, расчёт активных, инвариант погашения, невозможность второй привязки пользователя.
- [ ] Покрыто HTML/HTTP-тестами через Django test client (APIClient не нужен): анонимный `/`, `/login/` без публичной регистрации, доступность `mfss:contact`, сохранённый вход и восстановление пароля.
- [ ] Успех: автор выпускает ссылку, приглашённый видит ФИО автора и все прежние поля, регистрируется, сразу активен и вошёл, редирект на главную, письмо активации не отправлено.
- [ ] Профиль автора показывает только его действующие URL и использованные приглашения с ФИО и `date_joined`; профиль другого сотрудника не раскрывает эти записи. Несколько ссылок независимы, квота ограничивает лишь одновременно действующие.
- [ ] Неизвестный/испорченный токен, просроченный токен, URL без токена, повторный GET/POST после погашения и устаревшая ссылка активации не открывают форму и не создают пользователя; рядом ссылка на запрос доступа.
- [ ] Два параллельных POST с одним инвайтом на PostgreSQL (отдельные соединения/потоки и `transaction=True`): ровно один новый пользователь, ровно одно погашение, один успешный логин; ошибки `IntegrityError`/deadlock не становятся 500. Отдельно параллельный выпуск при N−1 проверяет, что лимит не превысится. Не помечать сценарий гонки проверенным только на SQLite.
- [ ] Проверка ошибок формы: при ошибке email/телефона/пароля инвайт остаётся активным, отправка email активации отсутствует. Тест сброса пароля подтверждает отправку штатного reset-письма.
- [ ] Отсутствуют N+1 запросы к БД в истории и активном списке; исключены открытые редиректы, утечка инвайт-токенов в логах и выдача чужой истории.
- [ ] `poetry run gate` завершается с кодом 0 (Ruff, basedpyright strict, pytest); тесты выполнять по `.agents/skills/test-pipeline/SKILL.md` и Django-команды — по `.agents/skills/docker-runner/SKILL.md`. Если доступная среда не позволяет запустить PostgreSQL, явно отметить непройденные конкурентные тесты в handoff, не объявлять критерий выполненным.
- [ ] Заполнен handoff-пакет по фактическому шаблону `.agents/handoffs/handoff-template.md` (пункт шаблона `reviews/handoff-[НОМЕР].md` уточнён по фактической структуре репозитория).
