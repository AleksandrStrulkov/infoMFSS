# SPEC-04: Исправление HTTPS/CSRF при регистрации по приглашению

Статус: утверждена Планировщиком для передачи Кодеру; реализация, тесты и проверка качества по этой спецификации ещё не выполнялись.

## 1. Цель
Исключить 403 CSRF verification failed при отправке формы регистрации по приглашению с HTTPS-страницы. Сейчас `RegisterView.dispatch` присваивает ответам `Referrer-Policy: no-referrer`: браузер не передаёт `Referer` в последующем POST, а Django при HTTPS без заголовка `Origin` требует корректный `Referer`. Политика `same-origin` сохраняет передачу `Referer` внутри сайта и не раскрывает путь с токеном приглашения при переходе на сторонний origin.

Важное уточнение: при наличии `Origin` Django сначала проверяет его; `Referer` проверяется при отсутствии `Origin`. Поэтому тест обязан моделировать именно HTTPS POST без `Origin` с корректным same-origin `Referer`, а не считать одну лишь смену заголовка доказательством успешного POST. Проверить также, что HTTPS POST без `Origin` и `Referer` остаётся отклонённым.

## 2. Границы задачи (Scope)
- Входит:
  - В `users/views.py`, в `RegisterView.dispatch`, заменить значение `Referrer-Policy` с `no-referrer` на `same-origin` для ответа с действительным приглашением и для страницы недействительного приглашения; оставить `Cache-Control: private, no-store`.
  - Обновить существующие проверки заголовка в `tests/tests_deploy/test_invite_registration.py`, добавить регрессионный тест реального HTTPS-сценария с включённой CSRF-проверкой. Проектный каталог для стабильных тестов — `tests/tests_deploy/`; `users/tests.py` существует, но пуст. Не создавать новый каталог `users/tests/` без отдельной причины.
- НЕ входит:
  - Отключение CSRF, изменение `CSRF_TRUSTED_ORIGINS`, cookie/security/proxy-настроек или общего middleware; ослабление `Referer`/`Origin`-проверок.
  - Изменение маршрутов, модели и погашения приглашений, формы регистрации, бизнес-логики, шаблонов, политики для других представлений, оборудования и frontend.

## 3. Входные и выходные данные (Контракт)
- Эндпоинт: `GET|POST` именованного маршрута `users:register` (`/users/accounts/register/<token>/`); серверный HTML и form-urlencoded, не JSON API. Токен остаётся в пути, CSRF-токен — внутри формы.
- GET с действительным приглашением: `200`, форма; ответ содержит `Referrer-Policy: same-origin` и прежний `Cache-Control: private, no-store`.
- HTTPS POST с действительным приглашением, валидной формой и CSRF-cookie/токеном: при same-origin `Referer` (без `Origin`) проходит CSRF и возвращает обычный `302` на `mfss:home`, создаёт и аутентифицирует ровно одного пользователя, погашает приглашение. Ответ также содержит оба названных заголовка.
- HTTPS POST без корректной CSRF-пары или без `Origin` и `Referer` не должен проходить CSRF: `403`, пользователь не создан, приглашение не погашено. Не заменять `same-origin` на `unsafe-url` или политику отправки referrer на сторонние сайты.
- Недействительный/погашенный токен: сохранить существующий ответ со страницей ошибки и обоими заголовками; существующий HTTP-контракт регистрации и обработки ошибок формы остаётся неизменным.

## 4. Требования к данным и БД
- Затронутые модели: никаких изменений моделей; тест использует существующие `User` и приглашение через фабрику/сервис из `tests/tests_deploy/test_invite_registration.py`.
- Миграции: нет.
- Связи и выборки: без новых запросов, N+1 не добавлять. Проверить состояние пользователя и приглашения после POST, не менять механизм транзакционного погашения.
