Строгие требования к коду Python / Django:

1. Современная аннотация типов (PEP 484, PEP 585, PEP 604):
- Полная строгая типизация всех аргументов и возвращаемых значений функций и методов. Использование `Any` запрещено без обоснованного комментария.
- Современный синтаксис объединений и коллекций: `int | str` вместо `Union[int, str]`, `dict[str, Any]` и `list[str]` вместо `Dict`, `List` из typing.
- Для опциональных значений использовать только `str | None` вместо устаревшего `Optional[str]`.
- При возврате инстанса собственного класса использовать нативный тип или `Self` (`from typing import Self`).
- Учитывать типизацию Django ORM: использовать явные подсказки типов для QuerySet (`QuerySet[ModelName]`).

2. Принципы SOLID и чистая архитектура Django (info-mfss):
- Single Responsibility (S): Views и эндпоинты отвечают исключительно за HTTP-контракт (десериализация, статус-коды, вызов доменного слоя). Бизнес-логику, агрегацию и расчёты выносить строго в сервисы (`services.py`) или специализированные селекторы.
- Open/Closed (O): Использовать базовые сервисы и стратегии. Новое поведение добавляется новыми классами-обработчиками, а не разрастанием `elif` в существующих методах.
- Liskov Substitution (L): Наследники сервисов и репозиториев строго сохраняют контракт и сигнатуру базовых абстракций.
- Interface Segregation (I): Не создавать монолитных классов «всё-в-одном». Дробить функционал через специализированные миксины или `Protocol` из typing.
- Dependency Inversion (D): Доменная логика оперирует абстракциями и протоколами, не завязываясь на низкоуровневые детали реализации сторонних клиентов.
- Ограничение ORM в info-mfss: Учитывать переопределённые методы `.save()` у моделей `EquipmentInstallation`, `CableMagazine`, `Tunnel`, `BranchesBox`. Не использовать `bulk_update` или `QuerySet.update()`, если они ломают бизнес-логику автогенерации имён и слагов.

3. Оформление и стиль (PEP 8):
- Длина строки: строго до 119 символов (синхронизировано с конфигом Black и Flake8 в pyproject.toml).
- Именование: `snake_case` для функций, методов и переменных; `PascalCase` для классов; `UPPER_CASE_SNAKE` для констант.
- Осмысленные самодокументируемые имена без хаотичных сокращений (`power_distribution_unit` вместо `pdu_src`).
- Докстринги в формате Google/Sphinx для всех публичных методов сервисов, команд и сложных функций.

4. Проверка качества перед сдачей (Машинные арбитры Слоя 3 и Eval-петля Слоя 4):
Работа над кодом считается незавершённой, пока все машинные проверки не вернут код 0 (exit code = 0).

Основной способ сдачи задачи — единый прогон гейта:
- Локально:
 poetry run gate <path_to_file>
 (или полный прогон: poetry run gate)
- Внутри Docker:
 docker compose exec web poetry run gate <path_to_file>
 (или полный прогон: docker compose exec web poetry run gate)

При необходимости пошаговой отладки запускать арбитров раздельно:
1. Линтинг и сортировка импортов (Ruff на Rust):
 - poetry run ruff check <path_to_file>
2. Форматирование стиля (лимит строки 119):
 - poetry run ruff format --check <path_to_file>
3. Статическая типизация (строгий контракт basedpyright):
 - poetry run basedpyright <path_to_file>
4. Тесты и покрытие (для затрагиваемого модуля/эндпоинта):
 - poetry run pytest <path_to_test_file> --cov

Правила обработки результатов:
- Если запуск внутри Docker, использовать аналогичные префиксы: docker compose exec web poetry run...
- При любом ненулевом коде возврата агент обязан самостоятельно прочитать вывод stderr/stdout, исправить дефект и повторить прогон петли.
- Подавление ошибок линтера и тайпчекера через # type: ignore, # noqa или noqa: E501 без прямого технического согласования строго запрещено.
