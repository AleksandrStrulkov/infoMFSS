## 2. Оценка по 5-пунктной рубрике
1. **Соответствие контракту: PASS для проверенного скоупа, условие для выпуска.** Четыре первоначальных замечания ревью закрыты в коде/конфигурации; `web` больше не публикует порт в отслеживаемом Compose-файле. Фактическое закрытие старого порта после пересоздания на сервере ещё не подтверждено.
2. **Доказательства качества: ограниченный ISOLATED_PASS, не полный gate PASS.** `poetry run ruff check` — All checks passed для 12 Python-файлов SPEC-02; `ruff format --check` — 12 files already formatted. Повторённый изолированный pytest на PostgreSQL: **14 passed, 1 warning** о занятом соединении при удалении тестовой БД; запуск с `-o addopts=` не проверяет общий порог покрытия. `poetry run gate` завершился **exit code 1** на Ruff, в частности в неизменённых относительно базового SHA `infoMFSS/admin.py` и `infoMFSS/admin_import.py`; последующие этапы не выполнены. basedpyright strict, полный pytest и coverage ≥70% не получили подтверждения успешного прохождения; изоляция **всех** их возможных ошибок от SPEC-02 не доказана.
3. **Архитектурная чистота: PASS по ранее рассмотренному коду.** Выпуск и погашение сосредоточены в сервисе, инварианты — в модели/миграции; после форматирования новая независимая проверка архитектуры не проводилась.
4. **Скрытый техдолг: PASS с ограничением.** В первоначальном ревью не выявлены новые заглушки и логирование токена. Долг общего gate остаётся и требует отдельной задачи, а не объявления исправленным.
5. **Безопасность и данные: PASS в конфигурации файла, условие для действующего сервера.** В `docker-compose.yml` нет `web.ports`, `nginx` и `web` находятся в одной сети; HTTPS-ссылка за nginx проверена тестами ранее. Работающий локальный `web` всё ещё публикует `0.0.0.0:8001`/`[::]:8001`: удаление строки не закрывает уже работающий порт. Нельзя считать предпосылку доверенного `X-Forwarded-Proto` выполненной на сервере до проверки действующей сети и overrides. SQLi/N+1 в просмотренных путях не обнаружены, количественный тест N+1 отсутствует.

### Чеклист для человека на боевом сервере (POSIX shell; выполнять из каталога нужного Compose-проекта)

**До команд:** согласовать окно и доступ, доставить проверенный релизный commit, убедиться, что `.env` и TLS-сертификат соответствуют серверу. Если используются дополнительные `-f`/`COMPOSE_FILE`, задавать **один и тот же** набор файлов во всех командах ниже; без этого проверка локального файла не доказывает эффективную конфигурацию. При любом несоответствии остановиться, не пересоздавать сервис.

```sh
# 1. Проверить текущие контейнеры, эффективные порты и конфигурацию,
# не публикуя вывод `docker compose config` целиком: он может раскрыть секреты.
docker compose ps
docker compose config --format json | python3 -c 'import json,sys; s=json.load(sys.stdin)["services"]; print("web ports:", s["web"].get("ports", [])); print("web networks:", s["web"].get("networks", {})); print("nginx networks:", s["nginx"].get("networks", {}))'
# Ожидается: web ports: []; общая сеть web/nginx. Иначе STOP.

# 2. До любых изменений БД сохранить дамп в защищённом каталоге ВНЕ web-root.
# Подставить фактические имя БД и пользователя, предварительно проверенные по `.env`.
# Не применять автоматическое восстановление на живой базе.
umask 077
mkdir -p ../db-backups
# Подставить имена без кавычек только если они проверены администратором;
# пароль считывается pg_dump из окружения контейнера/настроенного pgpass.
docker compose exec -T db pg_dump -U '<DB_USER>' -d '<DB_NAME>' -Fc > ../db-backups/pre-spec-02.dump
test -s ../db-backups/pre-spec-02.dump && pg_restore -l ../db-backups/pre-spec-02.dump >/dev/null
# При ошибке или отсутствии pg_restore на хосте проверить дамп другим согласованным способом; иначе STOP.

# 3. Сверить миграционный план и наличие файла 0012 в доставленном релизе.
test -f users/migrations/0012_invitation.py
docker compose exec -T web python manage.py showmigrations users
docker compose exec -T web python manage.py migrate users --plan
# Если план содержит неожиданные операции — STOP и согласовать.

# 4. Только ПОСЛЕ отдельного разрешения на миграцию и подтверждённого дампа:
# Нельзя сначала пересоздать web: его entrypoint сам выполняет `migrate`
# и несколько команд заполнения данных при каждом запуске.
docker compose exec -T web python manage.py migrate users
docker compose exec -T web python manage.py showmigrations users
# Ожидается [X] 0012_invitation. При ошибке STOP, исследовать состояние БД.

# 5. Пересоздать web с актуальным кодом и новой сетевой конфигурацией.
# Пересборка нужна, если код не берётся из актуального bind mount на сервере.
docker compose up -d --no-deps --build --force-recreate web
docker compose ps
docker compose logs --tail=100 web
# Ожидается: web работает; нет публикации 8000 на 0.0.0.0, [::] или 127.0.0.1.

# 6. Проверить маршруты через nginx/TLS и HTTP-редирект (без токена в логах).
curl -fsSI https://<PUBLIC_HOST>/login/
curl -sSI http://<PUBLIC_HOST>/login/
# Внешний HTTP должен перенаправлять на HTTPS; login отвечает ожидаемо.
# Приглашение проверить вручную через браузер по HTTPS с тестовым аккаунтом;
# сам токен не вставлять в тикеты, shell history или команды curl.
```

После шага 5 на **другой внешней машине** проверить доступ к `http://<PUBLIC_HOST>:8001/` (IPv4 и IPv6, если есть): соединение должно быть недоступно. Проверить также `docker compose ps` на сервере и фактические Docker port bindings (`docker compose port web 8000` не должен возвращать опубликованный адрес). Если порт доступен, HTTPS не работает, отсутствует `[X] 0012_invitation` или entrypoint сообщает ошибку, **не выдавать приглашения**, остановить развёртывание и исправить конфигурацию/состояние; восстановление из дампа выполнять только по отдельному плану.
