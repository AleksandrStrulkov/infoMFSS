# Python Development Standards (info-mfss)

Стандарт разработки проекта info-mfss. Документ — единый источник проверяемых правил для разработчиков и AI-агентов.
Ссылки на параграфы вида «§5», «§10», «§13» используются в промптах ролей (code.md, refactor.md, reviewer.md).
Все правила обязательны для нового кода. Существующий код приводится к стандарту по мере касания (правило бойскаута).

Главные принципы
1. Читаемость прежде всего. Код чаще читают, чем пишут. Сложные list-comprehensions ради экономии строк запрещены; явный цикл for, если он понятнее, — приветствуется. Преждевременная оптимизация запрещена: ускорение логики допустимо только тогда, когда профилирование показало узкое место.
2. Без типов проект не пишется. Все функции, методы и свойства обязаны иметь аннотации входных параметров и возвращаемого типа, включая явное -> None. Инструмент basedpyright в strict-режиме обязателен.
3. Словари запрещены на границах. Тип dict запрещён как публичный контракт между слоями, модулями и функциями. Внутри одной функции dict допустим как промежуточная структура при парсинге. На границах слоёв — dataclass, Pydantic-схемы или доменные объекты.
4. Секреты не попадают в код и коммиты. Все доступы, пароли и ключи загружаются только через .env локально и переменные окружения в проде. Любой токен или пароль в settings.py, pyproject.toml или тестах — критический баг.
5. Перед коммитом проходит единый гейт. Локальный шорткат: poetry run gate (включает Ruff, basedpyright, pytest с coverage). Если проверка падает — коммит не создаётся.
6. Стек проекта — синхронный Django + DRF. Проект работает под управлением WSGI (Gunicorn) с пулом синхронных соединений PostgreSQL. Асинхронные вставки, вызовы async ORM и смешение async/sync без отдельной архитектурной спеки запрещены.

Запреты — нарушение блокирует merge

| # | Конструкция / Действие | Почему запрещено |
|---|---|---|
| 1 | except Exception: pass | Глушит ошибки без трассировки, маскирует баги в проде. Ловим конкретный тип либо логируем и пробрасываем. |
| 2 | def foo(items=[]) | Изменяемое значение по умолчанию (mutable default) общее для всех вызовов. Использовать None и проверку внутри. |

| 4 | Сырые SQL-запросы через f-строки | Прямая угроза SQL Injection. Использовать Django ORM или параметризованный cursor.execute(query, [params]). |

| 6 | Использование Optional, List, Dict из typing | Устаревший стиль. Использовать X \| None, list[X], dict[K, V] (стандарты PEP 604 и PEP 585). |

| 8 | Бизнес-логика во views.py или сериализаторах | Нарушает слои. View и Serializer отвечают за HTTP/валидацию, доменная логика живёт в services/. |
| 9 | Проблема N+1 при обращении к ForeignKey | Приводит к сотням лишних запросов к БД. Использовать select_related и prefetch_related. |
| 10 | Тяжёлые вызовы и HTTP внутри transaction.atomic | Блокирует строки и соединения с БД на время внешнего сетевого ответа. |
| 11 | # noqa и # type: ignore без комментария | Скрывают техдолг. Если подавление неизбежно, обязан быть комментарий с технической причиной. |
| 12 | Флаг --no-verify при коммите | Обход проверок качества. Если хук упал — ищем причину и исправляем код. |
| 13 | print() вместо логирования | Не имеет уровня важности и не попадает в сборщик логов. Использовать structlog / logger. |
| 14 | f-строки в сообщении логгера | Ломает группировку событий в ELK/Loki. Использовать стабильную строку и kwargs. |

§1. Типизация

Аннотации обязательны везде

Каждая сигнатура функции, метода и метода класса обязана иметь полную типизацию:
# Неправильно
def get_equipment_status(unit_id, include_offline=False):
    return {"unit_id": unit_id, "active": True}

# Правильно
def get_equipment_status(unit_id: int, include_offline: bool = False) -> EquipmentStatusDTO:
    return EquipmentStatusDTO(unit_id=unit_id, is_active=True)


Первая строка каждого Python-файла

Каждый файл исходного кода начинается с импорта:
from __future__ import annotations


Это включает отложенную оценку аннотаций типов, устраняет циклические импорты в тайпингах и гарантирует поддержку современного синтаксиса на уровне парсера.

Современный синтаксис типов (PEP 604 и PEP 585)

Запрещено импортировать Union, Optional, List, Dict, Tuple из модуля typing:
# Неправильно
from typing import Optional, List, Dict
def find_units(code: Optional[str]) -> List[Dict[str, int]]: ...

# Правильно
def find_units(code: str | None) -> list[dict[str, int]]: ...


Возврат None аннотируется явно

Функции и методы без возвращаемого значения обязаны декларировать тип:
def reset_counters(self) -> None:
    self._counters.clear()


Использование Protocol для слабой связанности

Сервисы должны зависеть от протоколов интерфейсов, а не от конкретных тяжелых реализаций:
from typing import Protocol

class SubstationProviderProtocol(Protocol):
    def get_layout(self, substation_id: int) -> SubstationLayoutDTO: ...


§2. Модели Django, DTO и Value Objects

В проекте действует строгое разделение ответственности по формату данных:

1. Django ORM Модель (models.Model): отвечает за хранение, схему таблиц, связи и транзакционную целостность в PostgreSQL.
2. DTO и Value Objects (@dataclass(frozen=True)): чистые структуры данных Python для переноса информации между слоями без привязки к ORM.
3. Сериализаторы DRF (serializers.Serializer): отвечают исключительно за валидацию входящего JSON из HTTP-запроса и форматирование исходящего JSON-ответа.

Правило: функции сервисного слоя не должны возвращать сырые Django QuerySet наружу в API-слой, если требуется сложная трансформация данных — возвращаются типизированные DTO.

Пример DTO:
from dataclasses import dataclass
from datetime import datetime

@dataclass(frozen=True)
class SubstationLayoutDTO:
    substation_id: int
    name: str
    voltage_kv: float
    is_operational: bool
    updated_at: datetime


§3. Обработка ошибок и исключений

Запрет глушения исключений

Категорически запрещены пустые блоки try/except pass. Любое пойманное исключение должно быть либо обработано, либо залогировано с контекстом, либо трансформировано в понятное доменное исключение:
python

Неправильно

try:
    node.calculate_load()
except Exception:
    pass

Правильно

try:
    node.calculate_load()
except CalculationError as err:
    logger.warning("load_calculation_failed", node_id=node.id, error=str(err))
    node.set_default_load()

### Принцип Fail Fast
Если приложение запущено с невалидными переменными окружения или конфигурацией — падать сразу на этапе инициализации Django, а не продолжать работать с непредсказуемым поведением.

### Семантика возврата None
Возврат None допустим только тогда, когда отсутствие данных является штатным бизнес-сценарием (например, объект не найден по коду). Если произошёл сбой сети, ошибка парсинга или недоступность БД — выбрасывается соответствующее исключение, а не возвращается None.

## §4. Принципы SOLID

1. Single Responsibility (SRP): каждый класс и модуль решает одну задачу. Представление (View) принимает запрос и отдаёт ответ; сервис выполняет бизнес-правило; сериализатор проверяет поля; модель хранит данные.
2. Open/Closed: добавление новых типов оборудования или схем подстанций реализуется через расширение классов или стратегий, а не через раздувание простыней if/elif.
3. Dependency Inversion: сервисный слой не должен напрямую зависеть от деталей конкретной сторонней интеграции. Используй протоколы или интерфейсы-адаптеры.

---

## §5. База данных, ORM и транзакции

Проект использует классический синхронный Django ORM.

### Защита от N+1
Все связи ForeignKey и OneToOne, к которым планируется обращение в сериализаторе или цикле, обязаны загружаться через select_related. Связи ManyToMany и обратные ForeignKey — через prefetch_related:
```python
# Неправильно (порождает N запросов в цикле)
feeders = Feeder.objects.filter(is_active=True)
for feeder in feeders:
    print(feeder.substation.name)

# Правильно (один SQL-запрос с JOIN)
feeders = Feeder.objects.filter(is_active=True).select_related("substation")


Атомарность транзакций

Все операции изменения данных, затрагивающие несколько таблиц или несколько строк, объединяются в транзакцию:
from django.db import transaction

with transaction.atomic():
    substation.save()
    EquipmentLog.objects.create(substation=substation, action="updated")


Правило короткой транзакции

Внутри блока transaction.atomic() строго запрещено выполнять внешние сетевые вызовы (HTTP-запросы к внешним API, отправку писем, долгие вычисления). Транзакция должна удерживать соединение с БД минимально возможное время.

§6. Простота кода (KISS)
1. Длина функции не должна превышать ~40 строк кода. Если функция больше — она делает слишком много.
2. Максимальный уровень вложенности блоков (if, for, try) — 3. При большей вложенности код декомпозируется или используется ранний возврат (Early Return):
```python

Неправильно

def process(unit: Unit | None) -> None:
    if unit:
        if unit.is_active:
            if not unit.is_locked:
                unit.run()

Правильно

def process(unit: Unit | None) -> None:
    if not unit or not unit.is_active or unit.is_locked:
        return
    unit.run()
3. Избегать аргументов-флагов (mode="fast", is_dry_run=True). Если функция ведёт себя принципиально по-разному в зависимости от булева флага — напиши две раздельные функции.

## §7. Повторное использование (DRY)

Общая логика форматирования данных, математических расчётов или проверок выносится в пакет helpers/ или utils/.
Применяется «правило трёх»: дублирование логики в двух местах допустимо, если абстракция неочевидна. При появлении третьего дубля — обязательный рефакторинг с выносом в общую функцию.

## §8. Соглашения по именованию

| Элемент | Стиль | Пример |
|---|---|---|
| Функции и методы | snake_case | calculate_voltage, get_by_substation |
| Классы, DTO, Модели | PascalCase | ElectricalSubstation, LayoutDTO |
| Константы уровня модуля | UPPER_SNAKE_CASE | MAX_BUSBAR_LOAD, DEFAULT_TIMEOUT_SECONDS |
| Булевы переменные и поля | Префиксы is_, has_, can_ | is_operational, has_backup_line |
| Защищённые атрибуты/методы | Префикс _ | _recalculate_internal_cache |

Магические значения запрещены:
```python
# Неправильно
if voltage &gt; 110:
    ...

# Правильно
HIGH_VOLTAGE_THRESHOLD_KV: float = 110.0

if voltage &gt; HIGH_VOLTAGE_THRESHOLD_KV:
    ...


§9. Сигнатуры и аргументы функций
1. Изменяемые значения по умолчанию запрещены:
# Неправильно
def collect_metrics(tags: list[str] = []) -&gt; list[str]: ...

# Правильно
def collect_metrics(tags: list[str] | None = None) -&gt; list[str]:
    active_tags = tags if tags is not None else []
    ...


2. Количество параметров функции не должно превышать 4–5. Если требуется больше данных, они объединяются в dataclass.

§10. Слоевая архитектура info-mfss

Кодовая база разделена на изолированные слои. Импорты разрешены только сверху вниз:

API Layer (views.py, urls.py, serializers.py)
  ↓
Service Layer (services/)
  ↓
Repository / Query Layer (managers, repositories, querysets)
  ↓
Domain & Database Layer (models.py, DTO)

Правила зависимостей:
- api/ вызывает services/ и оперирует сериализаторами. Внутри views запрещено писать сложные ORM-запросы и фильтрации.
- services/ содержит чистую бизнес-логику и оркестрацию. Сервис ничего не знает про HTTP-запросы, request.META или статус-коды.
- models.py определяет структуру таблиц и базовые свойства. Не импортирует сервисы и представления.

§11. Миграции базы данных
1. Любое изменение полей моделей Django сопровождается миграцией, сгенерированной через poetry run python manage.py makemigrations.
2. Файлы миграций обязательно добавляются в коммит вместе с изменениями в models.py.
3. Миграции должны быть обратимыми и безопасными для данных. Удаление колонок или таблиц выполняется в два этапа (deprecation cycle).
4. Ручная модификация схемы базы данных в PostgreSQL в обход файлов миграций Django запрещена.

§12. Внешние сетевые вызовы
1. Все HTTP-запросы во внешние сервисы выполняются с явным указанием timeout=:
import requests

response = requests.get("http://internal-telemetry/api/v1/data", timeout=5.0)


2. Запрещено отключать валидацию сертификатов (verify=False). Если используется корпоративный внутренний центр сертификации, передаётся путь к CA: verify="/etc/ssl/certs/corp-ca.crt".
3. Для критичных внешних вызовов реализуются повторные попытки (retry) с экспоненциальной задержкой.

§13. Логирование
1. Использование print() в коде проекта категорически запрещено. Для локальной отладки используется breakpoint(), для фиксации событий — логгер.
2. Сообщения логов оформляются константной строкой события (event string), а динамические данные передаются через kwargs:
```python

Неправильно

logger.info(f"Подстанция {substation_id} отключена оператором {user_id}")

Правильно

logger.info("substation_disconnected", substation_id=substation_id, operator_id=user_id)
3. Запрещено логировать пароли, токены, ключи API и конфиденциальные данные. Поля password, token, secret в kwargs логгера запрещены.
4. Конфигурация логирования задаётся централизованно в settings.py. Модули вызывают только logging.getLogger(__name__) или structlog.get_logger().

## §14. Безопасность и выполнение процессов

1. SQL Injection: никакой склейки строк в SQL. Использовать параметры запроса.
2. Command Injection: при запуске внешних утилит операционной системы запрещено использовать shell=True с внешними аргументами:
```python
# Неправильно
subprocess.run(f"ping {host}", shell=True)

# Правильно
subprocess.run(["ping", "-c", "4", host], check=True)


3. Конфиденциальность: файлы .env, секретные ключи Django и дампы с реальными персональными данными никогда не добавляются в Git.
