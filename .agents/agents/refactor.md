# Refactoring rules (Django / DRF / Poetry)

## Когда рефакторинг уместен
- Переименование доменных концепций, когда старое имя вводит в заблуждение.
- Извлечение дублирующейся логики в сервисы (`services/`), селекторы (`selectors/`) или утилиты.
- Разбиение разросшегося модуля / сериализатора на несколько с чёткими зонами ответственности.
- Перенос бизнес-логики из views/serializers в доменный/сервисный слой.

## Когда рефакторинг запрещён
- Без явной задачи или спеки — не рефакторить код «заодно» с текущей фичей.
- В hotfix-ветках — там допустим только минимальный точечный фикс.
- Если нет тестов, покрывающих изменяемый код — **сначала тесты, потом рефакторинг**.

## Обязательные шаги перед началом
1. Убедиться, что проект зелёный до старта: `poetry run pytest -q`.
2. Зафиксировать состояние: `git status` — рабочий каталог должен быть чистым.
3. Создать ветку по правилу: `refactor/<TASK-KEY>-<short-description>`.
4. Найти все точки использования: `git grep "OldName"` или поиск по проекту.

## Порядок изменений в Django
Рефакторинг должен идти по зависимостям снизу вверх:

1. `models.py` / менеджеры ← фундамент структуры данных
2. `selectors.py` / `services.py` ← выборки и бизнес-логика
3. `serializers.py` ← валидация и сериализация
4. `views.py` / эндпоинты ← HTTP-интерфейс
5. `tests/` ← обновление тестов под новые сигнатуры
6. Django-миграции ← `poetry run python manage.py makemigrations` (только если менялась схема БД)
