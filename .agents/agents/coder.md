# Code rules (Django / DRF / Poetry)

- Всегда использовать from __future__ import annotations.
- Каждая функция и метод должны иметь аннотации типов.
- Если функция ничего не возвращает, явно писать -> None.
- Использовать современный синтаксис Python 3.12+:
 - X | None вместо Optional[X]
 - list[str] вместо List[str]
- Писать понятный и короткий код без лишней сложности.
- Если логика повторяется — выносить в helper-функции или сервисный слой.
- Не смешивать HTTP-логику (views/serializers), бизнес-логику и работу с базой данных в одном месте.

## Входные данные (что читать перед началом работы)
1. Основной контекст проекта и стек: `.agents/AGENTS.md`
2. Спецификацию задачи (SPEC): строго файл `.agents/specs/SPEC-<NN>-<name>.md` (где NN — номер текущей задачи).
3. Кодер НЕ начинает писать код, пока полностью не прочитает указанный файл спецификации.

## Общие принципы

### PEP 8 и форматирование
- Следовать PEP 8 (отступы 4 пробела, максимальная длина строки — 119 символов, как задано в pyproject.toml).
- Форматирование и импорты — строго через Ruff. Вручную со стайлчекером не спорить.
- Осмысленные имена: `equipment_repository` лучше `er`, `get_active_substations()` лучше `gas()`.

### KISS — Keep It Simple, Stupid
- Выбирать самое простое решение, закрывающее задачу из спеки.
- Не строить абстракции «про запас» — расширять код только по факту появления нового кейса.
- Функция решает одну задачу. Если в названии просится `and` — разбить на две.
- Если коду требуется длинный комментарий с объяснением логики — код нужно отрефакторить и упростить, а не комментировать.

### DRY — Don't Repeat Yourself
- Повторяющаяся бизнес-логика выносится в сервисы (`services/`) или утилиты (`utils/`) — единая точка правды.
- Повторяющиеся константы, статусы и коды выносятся в `TextChoices` / `IntegerChoices` моделей или модули `constants.py`.
- DRY не отменяет KISS: не объединять разнородную логику в монструозные функции с кучей булевых флагов.

### SOLID в контексте Django / DRF
- **S (Single Responsibility)**: ViewSet отвечает за прием HTTP-запроса и ответ; Serializer — за валидацию данных и сериализацию; Service/Manager — за доменную логику; Модель — за структуру данных и целостность.
- **O (Open/Closed)**: расширять логику через новые сервисы, кастомные permissions или фильтры, а не раздувать ветки `if/elif` в старых методах.
- **L (Liskov Substitution)**: методы менеджеров и сервисов должны возвращать предсказуемые типы (например, `QuerySet[Equipment]` или `None`), не ломая контракты.
- **I (Interface Segregation)**: сериализаторы не должны тянуть лишние поля; делать легковесные сериализаторы под конкретные эндпоинты (List vs Detail vs Create).
- **D (Dependency Inversion)**: бизнес-логика не должна намертво привязываться к деталям запроса (`request.META` и т.д.); передавать чистые доменные типы или аргументы.

## Архитектура слоев в Django

- **HTTP / API (`views.py`, `viewsets.py`, `serializers.py`)**: валидация входных данных, проверка разрешений (DRF Permissions), маппинг доменных ошибок в HTTP-статусы.
- **Бизнес-логика (`services.py` / `domain/`)**: оркестрация операций, транзакции, интеграции, расчеты. Никаких прямых обращений к объекту `request`.
- **Данные и ORM (`models.py`, `managers.py`, `selectors.py`)**: выборки через Django ORM, инкапсуляция сложных фильтров.
 - Обязательно избегать проблемы N+1: всегда использовать `select_related` для связей FK / OneToOne и `prefetch_related` для ManyToMany / обратных связей.

## Возвраты и ошибки

- Методы выборок (selectors) могут возвращать `Model | None`.
- API-слой обязан превращать отсутствие объекта в корректный 404 Not Found (например, через `get_object_or_404` или явный raise `NotFound`).
- Не глушить ошибки: категорически запрещено писать `except Exception: pass`.
- Если входные данные невалидны — выбрасывать `serializers.ValidationError` (в API) или доменное исключение с последующим перехватом.

## Запрещено

- Писать тяжелые вычисления и сырые SQL-запросы прямо во `views.py`.
- Выполнять ORM-запросы к БД внутри циклов и внутри методов `to_representation` сериализаторов (приводит к N+1).
- Использовать `print()` вместо вызова логгера (`logger.info`, `logger.error`).
- Дублировать одну и ту же бизнес-логику между Django Admin, API и Management-командами.

## Линтеры, гейты и качество кода

- Перед завершением любой задачи обязательно прогонять единый гейткипер:
 - `poetry run gate` (или точечно: `poetry run gate infoMFSS/path_to_file.py`).
- Для быстрого локального автофикса форматирования и сортировки импортов использовать:
 - `poetry run ruff check --fix <target>`
 - `poetry run ruff format <target>`
- Все проверки в гейте (Ruff, basedpyright, Pytest + Coverage >= 70%) ДОЛЖНЫ вернуть код 0.
- Не глушить предупреждения через `# noqa` или `# type: ignore` без явного согласования и комментария-обоснования.

## Pre-commit и зависимости

- Флаг `git commit --no-verify` строго запрещен.
- Если pre-commit или линтер упал на твоих изменениях — исправить дефект самостоятельно до финального отчета.
- Если обнаружена уязвимость в зависимостях (`poetry.lock`), обновление пакета выносится в отдельный изолированный коммит вида:
 `chore(deps): обновить <package> до X.Y.Z для закрытия CVE-XXXX-XXXXX`.
