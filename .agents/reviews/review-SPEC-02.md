Но абсолютные ссылки строятся с неверной схемой за HTTPS-прокси, а ответ при конкурентном погашении не выставляет защитные заголовки; оба пункта требуют исправления. 3. **N+1:** история использует `select_related('registered_user')`, пригласивший — `select_related('created_by')`; явного N+1 в этих местах не найдено. Тестов количества запросов нет, так что отсутствие N+1 при будущих изменениях не закреплено.

Гейт не подтверждён, stale-шаблон активации и слабые assertions оставлены. В проверенных фрагментах нет raw SQL/SQL-инъекции; доменные операции выпуска/погашения вынесены в services.
5. **Атомарность погашения:** `select_for_update` и повторная `is_valid()` внутри `transaction.atomic()` вместе с сохранением пользователя и связи предотвращают двойное погашение в PostgreSQL; `IntegrityError` откатывает транзакцию и переводится в безопасную ошибку. Вход выполняется после выхода из atomic. Тест параллельного POST не проверяет идентичность вошедшего клиента и не синхронизирует начало запросов, поэтому формулировка handoff сильнее доказательств.

## 3. Критические блокеры первоначального ревью (Must Fix)
1. **`users/views.py:133-135`, `config/settings.py:43,270-275`, `nginx/nginx.conf:48-52`:** `build_absolute_uri()` определяет схему по `request.is_secure()`, но прокси передаёт `X-Forwarded-Proto: https`, а `SECURE_PROXY_SSL_HEADER` не настроен. На HTTPS-сайте профиль сформирует приглашение с `http://...` и выдаст его в интерфейсе. Переход по ссылке сначала отправляет bearer-токен по HTTP (и включает его в URL редиректа), что нарушает требование безопасной схемы. Настроить доверенный HTTPS-прокси/проверенный публичный origin и проверить конечную абсолютную ссылку через сценарий прокси.
2. **`users/views.py:100-105`:** при погашении в гонке `form_valid` возвращает новый `render(...)`, обходя установку `Referrer-Policy: no-referrer` и `Cache-Control: private, no-store` в `dispatch`. Клиент, получивший уже использованный токен при параллельном POST, получает страницу по URL с секретом без этих заголовков. Использовать единый механизм выставления заголовков для всех ответов и регрессионно проверить как успешный, так и конфликтный POST.
3. **`users/urls.py:25`, `config/urls.py:26`, `tests/tests_deploy/test_invite_registration.py:114-118`:** `reverse('users:login')` остаётся `/users/`, а `/login/` зарегистрирован вне namespace. Старый `/users/` показывает форму вместо оговорённого redirect; гость с `/` попадает на `/users/?next=/`. Финальный выбранный контракт SPEC-02 §3 прямо требует `users:login → /login/`, совместимый `/users/ → /login/` с безопасным `next`. Тест закрепляет старое поведение, а не выявляет нарушение. Перенести имя маршрута в namespace с сохранением рабочего входа и проверить next/POST-клиентов.
4. **`users/templates/users/activation_failed.html:14-17`:** старый публичный шаблон по-прежнему предлагает «Зарегистрироваться повторно» через `{% url 'users:register' %}` без обязательного `token`; при рендере возникает `NoReverseMatch`. Хотя старый URL активации удалён, §2 SPEC-02 отдельно требует убрать старые ссылки на регистрацию, включая этот шаблон. Заменить ссылкой запроса доступа либо удалить неиспользуемый шаблон.

### Проверка четырёх Must Fix
1. **HTTPS за прокси — частично устранён, остаётся блокер безопасности.** `config/settings.py:45` задаёт `SECURE_PROXY_SSL_HEADER`, nginx в `nginx/nginx.conf:51` принудительно передаёт `X-Forwarded-Proto: https`, а тест `test_invitation_link_uses_https_behind_proxy` подтверждает HTTPS URL в профиле. Но `docker-compose.yml:33-34` публикует порт приложения на всех интерфейсах (`8001:8000`); прямой HTTP-клиент может прислать `X-Forwarded-Proto: https`, минуя nginx. Более существенно, приложение остаётся доступным по HTTP в обход обязательного nginx-редиректа: запрос на `http://<host>:8001/users/accounts/register/<token>/` передаёт одноразовый bearer-токен незашифрованным. `ALLOWED_HOSTS` допускает публичный host. Условие доверия к прокси, указанное самим handoff, в текущем compose не выполнено. До production-применения закрыть прямой внешний доступ к `web` (например, убрать публикацию порта или привязать к loopback с ограничением доступа) и проверить реальную сетевую конфигурацию; не считать защищённую выдачу/погашение ссылок доказанной для текущего развёртывания.
2. **Заголовки — устранено.** `RegisterView.dispatch` выставляет `Referrer-Policy: no-referrer` и `Cache-Control: private, no-store` после возврата из всех своих веток, включая результат `render` при конфликтном POST (`users/views.py:101-109,117-124`). Тесты проверяют оба заголовка на успешном, повторном и параллельном POST. Статус `405` для неподдерживаемого метода генерируется внутри dispatch и также проходит через выставление заголовков; непойманные серверные исключения не проверялись.
3. **URL-контракт — устранено для проверенных маршрутов.** Именованный `/login/` задан через `config/urls.py:27-36`, `reverse('users:login')` и редирект анонимного `/` проверены тестами. `LegacyLoginRedirectView` пропускает `next` только через `url_has_allowed_host_and_scheme` и кодирует его, старый POST аутентифицируется на месте без редиректа тела запроса (`users/views.py:47-61`). Тесты покрывают безопасный/враждебный `next`, новый и старый POST. Осталась неканоническая доступность `/users/login/` из `users/urls.py:27` из-за переподключения всех patterns под `/users/`; это не меняет имя `users:login`, но маршрут стоит убрать/явно задокументировать при упрощении URLconf.
4. **Старый шаблон — устранено.** `activation_failed.html` использует `mfss:contact`; тест рендерит его и проверяет ссылку, так что прежнего `NoReverseMatch` из-за `users:register` больше нет. Старый маршрут активации отсутствует.
